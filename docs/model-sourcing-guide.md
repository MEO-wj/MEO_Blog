# 模型获取与资产整理指南

## 1. 文档目的

这个仓库当前聚焦于 3D 模型布局编辑器，因此“找模型”和“整理模型”的目标需要围绕编辑器工作流来组织。

现在我们重点关注的是：

- 哪些模型能稳定进入编辑器
- 哪些文件应该被视为原始资产
- 哪些模型已经整理到可直接摆放
- 后续 AI 生成模型应该怎么接入现有流程

这份文档的目标，是把模型资产的流转路径统一下来。

## 2. 支持的模型格式

当前编辑器优先支持：

- `.glb`
- `.gltf`
- `.fbx`
- `.obj`

优先级建议：

1. `GLB`
2. `glTF`
3. `FBX`
4. `OBJ`

原因：

- `GLB/glTF` 更适合 Web 侧实时加载
- 材质和贴图链路通常更清晰
- 更容易做统一入库

## 3. 目录约定

### 原始资产

```text
external-assets/raw/
```

用于存放：

- 第三方下载包
- AI 生成原始结果
- 自己导出的未整理模型

这里的文件不要求命名统一，也不要求直接可用。

### 清洗后资产

```text
external-assets/processed/
```

用于存放：

- 拆分后的子模型
- 减面后的版本
- 重新命名后的模型
- 补齐材质后的中间结果

### 最终发布资产

```text
public/models/
```

用于存放：

- 编辑器直接加载的最终模型
- 命名稳定、比例明确、便于复用的资源

这个目录应视为“场景编辑器的正式资产库”。

## 4. 推荐入库流程

### 步骤 1: 收集模型

把外部模型先放进 `external-assets/raw/` 下合适的子目录，例如：

```text
external-assets/raw/
|-- props/
|-- furniture/
|-- characters/
|-- vehicles/
|-- ai/
```

### 步骤 2: 记录来源和授权

在 `external-assets/licenses/` 中记录：

- 来源链接
- 作者
- 下载日期
- 授权方式
- 是否允许商用
- 是否允许二次分发

### 步骤 3: 清洗模型

在 Blender 或其他 DCC 中进行：

- 统一缩放
- 删除无关节点
- 拆出独立对象
- 修复贴图引用
- 适度减面
- 统一命名

### 步骤 4: 放入 processed

将中间结果放入：

```text
external-assets/processed/
```

### 步骤 5: 生成最终可用模型

确认模型适合在编辑器中稳定加载后，再放进：

```text
public/models/
```

### 步骤 6: 更新素材清单

运行：

```bash
npm run models:manifest
```

这样编辑器可以重新识别 `public/models/` 中的新资产。

## 5. 命名建议

### 正式资产命名

推荐使用：

```text
<category>/<asset-name>.glb
```

例如：

```text
public/models/props/table-lamp.glb
public/models/vehicles/forklift.glb
public/models/furniture/lounge-chair.glb
```

### 命名原则

- 小写
- 用 `-` 分隔
- 避免空格
- 避免中文文件名进入最终发布目录
- 名称尽量表达用途而不是来源网站

## 6. 资产入库标准

模型进入 `public/models/` 前，建议至少满足：

- 加载路径稳定
- 原点合理
- 缩放大体可信
- 材质不报错
- 贴图引用完整
- 面数适合实时预览

如果某个模型还只能“勉强打开”，但不能稳定放进编辑器，那就不要放到 `public/models/`。

## 7. 适合进入编辑器的资产类型

### 当前优先

- 可单独摆放的静态道具
- 家具、器件、容器、展示件
- 简单角色或雕像
- 场景装饰件

### 谨慎进入

- 超大场景整包
- 贴图引用复杂的多文件资产
- 面数极高的扫描模型
- 动画绑定特别复杂的角色

这些资产可以先放在 `raw/` 或 `processed/`，等后续有更成熟的处理流程再纳入编辑器。

## 8. 本地上传与正式入库的区别

### 本地上传

适用于：

- 临时试摆
- 快速验证一个模型是否值得入库
- 尚未整理好的素材

特点：

- 只在当前浏览器会话中有效
- 不保证后续恢复时依然存在
- 更像“临时素材”

### 正式入库

适用于：

- 后续要长期复用
- 要参与布局 JSON 的稳定恢复
- 要作为 AI 或脚本的稳定输入

特点：

- 路径固定
- 命名清晰
- 能被仓库扫描识别

## 9. AI 生成模型接入规范

后续如果接入 AI 生成 3D 模型，建议不要直接把结果丢进 `public/models/`。

推荐流程：

1. 原始生成结果进入 `external-assets/raw/ai/`
2. 记录模型生成提示词和生成时间
3. 标记生成工具和版本
4. 人工或脚本清洗后再进入 `processed/`
5. 确认可用后再进入 `public/models/`

建议额外记录：

- prompt
- seed
- generator name
- generator version
- post-process notes

## 10. 现有脚本的用途

### `scripts/generate-model-manifest.mjs`

用途：

- 扫描 `public/models/`
- 生成模型清单
- 供编辑器素材面板读取

### `scripts/split_glb_by_roots.py`

适用于：

- 某个 GLB 里塞了多个根对象
- 想拆成多个可独立摆放的资产

它适合资产整理阶段，不适合直接作为布局编辑阶段脚本调用。

## 11. 资产检查清单

每次准备把模型从 `processed/` 移到 `public/models/` 时，建议快速检查：

- 是否能在编辑器中打开
- 缩略图是否正常生成
- 原点是否合理
- 默认尺寸是否符合预期
- JSON 恢复后是否仍能正确重载
- 是否已经有来源和授权记录

## 12. 结论

对于这个仓库，模型获取不是单独的收藏行为，而是编辑器生产链路的一部分。

判断一个模型是否“已经准备好”的标准，不是它看起来够不够精细，而是：

- 它能不能稳定进入编辑器
- 能不能被布局 JSON 正确引用
- 能不能被后续脚本或 AI 流程继续消费

如果满足这三点，它才算真正进入了这个仓库的有效资产体系。
