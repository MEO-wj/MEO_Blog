# Switch 主页网页游戏接入开发方案

日期：2026-09-30

状态：选型与开发规划，尚未实施

范围：桌面端 Switch 主页内置《塞尔达传说》与《超级马里奥兄弟》网页复刻版

## 1. 选型结论

建议以 **FullScreenMario 作为马里奥的技术首选，以 ZQuest Classic 现成 Web 版搭配初代复刻任务作为塞尔达的技术预选**。两者都可以研究源码并自行部署，不需要把 NES 模拟器作为本次方案的基础。

需要保留一个明确的区别：马里奥找到了较贴合要求的 HTML5/JavaScript 复刻；塞尔达尚未找到同时经过核实、内容完整、许可清楚、无需访客提供 ROM 的纯 JavaScript 即用项目。ZQuest Classic 已有浏览器版本，但采用 C++ 编译到 WebAssembly 的路线，接入成本高于普通 JS 游戏。它是游戏引擎及任务内容的复刻路线，不是 JSNES 一类 NES 硬件模拟器。

| 游戏 | 本次选定的研究、验证对象 | 决策状态 | 正式接入前必须解决的问题 |
| --- | --- | --- | --- |
| 超级马里奥兄弟 | [dataquestio/FullScreenMario](https://github.com/dataquestio/FullScreenMario) | 技术首选 | 老代码在现代浏览器的兼容性、可靠的进度存档适配、代码与素材的发布条件 |
| 塞尔达传说 | [ZQuest Classic](https://github.com/ZQuestClassic/ZQuestClassic) 的 [Web Player](https://web.zquestclassic.com/play/)，搭配下文的 `1stClassic.qst` 候选内容 | 技术预选，先做可行性验证 | 任务与当前引擎兼容、页面隔离响应头、暂停/保存接口、内容授权范围 |
| 塞尔达的纯 Web 源码备选 | [bobbylight/ZeldaJS](https://github.com/bobbylight/ZeldaJS) | 仅适合作为原型或二次开发基础 | 内容仍在开发，不能直接当成完整初代交付 |

本次完成的是上游文档、许可证、关键源码和本仓库接入位置的静态调研。**没有运行或通关候选游戏，没有实测下载体积与帧率，也没有验证保存后恢复效果。** 下文将这些工作列为开发阶段的验收项，不把项目介绍等同于实测结果。

## 2. 已确定的产品要求

| 项目 | 要求 |
| --- | --- |
| 入口 | 桌面端 Switch 主页面最前面的两个图标为塞尔达、马里奥；本方案按这个顺序排列 |
| 打开方式 | 点击图标，或键盘选中后按 Enter，直接进入对应游戏；不经过项目详情或游戏大厅 |
| 呈现位置 | 留在博客的 Switch 屏幕体验中，沿用现有屏幕聚焦与返回流程 |
| 游戏来源 | 优先复用已有网页复刻源码，避免从零重写完整游戏或重新移植一个只有 PC 版的项目 |
| 操作 | 电脑键盘即可游玩，提供按键说明、暂停、继续和返回主页 |
| 存档 | 只保存在访客自己的浏览器中，不上传本站服务器或第三方服务 |
| 移动端 | 本期不提供游戏入口、触屏控制及游戏运行资源加载；移动端仍使用现有博客界面 |
| 本次工作 | 只形成本文档，不接入游戏、不安装游戏依赖、不修改业务代码或部署配置 |

下文的按键映射、存档槽数量、内部目录和协议名称是开发建议，不代表用户已经指定这些细节。

原有 [Switch 主界面设计](./switch-interface-1-design.md) 中“当前不使用游戏图标”的旧约束，由这次明确提出的两个游戏入口需求更新；其余既有博客功能继续沿用。

## 3. 可复用项目与取舍

### 3.1 马里奥：FullScreenMario

项目 README 将其描述为原版《超级马里奥兄弟》的 HTML5/JavaScript 复刻，包含原版 32 个关卡，并提供地图编辑器、随机地图与模组。本期只考虑经典关卡玩法，额外工具不作为博客首屏功能。[项目说明](https://github.com/dataquestio/FullScreenMario#readme)

| 项目 | 调研结果与开发处理 |
| --- | --- |
| 源码入口 | `FullScreenMario.js`、`GameStartr/`、`settings/`，配套声音、字体与页面资源 |
| 运行方式 | 浏览器中的 JS 游戏；不以加载 `.nes` ROM 为启动条件 |
| 上游形态 | 较老的 Grunt 工程及全局游戏实例；作为独立游戏运行页接入，不直接塞进 React 组件内部 |
| 可复用范围 | 游戏规则、角色行为、碰撞、关卡、画面与音频播放逻辑；具体素材是否可随站发布另行核对 |
| 本站需要补充 | 启停适配、焦点与按键、暂停与静音、进度保存/恢复、资源路径和生命周期清理 |
| 调研版本 | `96a1e362dc9472f4a3d0bf7307bc9ffbc03c8bb4`；用于定位此次审阅，实际引入后继续固定版本 |

上游使用署名、非商业、相同方式共享的 Creative Commons 许可，不能按 MIT/Apache 项目处理。引入时保留许可证、作者信息及修改记录，并逐项整理其子模块许可。[README 的许可说明](https://github.com/dataquestio/FullScreenMario#legal)、[许可证原文](https://github.com/dataquestio/FullScreenMario/blob/master/LICENSE.txt)

源码中的运行器提供暂停/继续能力，但持久化统计数据不等于完整游戏存档。需要在关卡转换、玩家状态和安全重生位置之间建立可恢复的数据模型，不能仅把现有 `localStorage` 数据复制出来就宣称支持断点续玩。[运行器源码](https://github.com/dataquestio/FullScreenMario/blob/master/GameStartr/GamesRunnr/GamesRunnr.js)、[统计配置](https://github.com/dataquestio/FullScreenMario/blob/master/settings/statistics.js)

### 3.2 塞尔达：ZQuest Classic Web + 初代复刻任务

ZQuest Classic 是 GPLv3 开源游戏引擎，官方已经提供实验性的浏览器版本。拟复用它现成的 Web Player，而不是从头把桌面程序移植到浏览器。只构建、部署玩家运行部分，不把任务编辑器一起装进博客。[引擎仓库](https://github.com/ZQuestClassic/ZQuestClassic)、[Web 构建说明](https://github.com/ZQuestClassic/ZQuestClassic/blob/main/docs/building.md)

**具体内容候选：Anthus 的 TLoZ 2.5 Classic + Koten 1.3，优先使用 Classic 风格的第一任务。** 作者页面说明包含初代的两个任务，任务文件未加编辑密码，并允许随 ZC 分支打包使用。这里的“可编辑内容”是 `.qst` 任务数据；运行规则的程序源码在引擎仓库中。[作者发布页](https://www.purezc.net/index.php?page=quests&id=591)

| 项目 | 定位 |
| --- | --- |
| 引擎调研版本 | `8ef6a707145eb455331aa3ee101724eaf3bc470f`；正式版本需通过下面的验证后锁定 |
| 内容作者/版本 | Anthus / TLoZ 2.5 Classic + Koten 1.3 |
| 官方 Web 目录中的任务 ID | `quests/purezc/591` |
| 目录中的默认文件路径 | `quests/purezc/591/r01/1stClassic.qst` |
| 本期内容目标 | 初代第一任务；第二任务不作为首期必须交付项 |
| 内容编辑 | 用上游编辑器检查任务数据，运行时不部署编辑器 |
| 访客启动条件 | 部署时准备好经过核对的引擎与任务资源，访客不需要自行寻找或上传 ROM |

上述任务 ID 与路径来自 [官方 Web 资源目录](https://data.zquestclassic.com/manifest.json)，并非猜测的下载文件名。正式引入时要保存内容版本、实际文件列表和校验值，不依赖第三方目录永远保持不变。

这个候选有三个限制需要在开工初期解决：

1. 作者发布页对应 ZC 2.50.2；当前 Web 引擎的兼容性仍需验证。任务在目录中出现，只能证明已有索引，不能证明它在当前浏览器构建中完整可通关。
2. 官方 Web Player 明确标注实验状态；本期必须验证音频、键盘、保存恢复与反复启动退出。[Web Player 说明](https://web.zquestclassic.com/play/)
3. 当前 Web 构建配置含 `-pthread`、共享内存和线程池。必须先验证博客顶层页面的跨源隔离与嵌入方式，不能仅创建 iframe 就认定能运行。[构建脚本](https://github.com/ZQuestClassic/ZQuestClassic/blob/main/scripts/configure_emscripten.sh)

作者允许复用其任务贡献，不等于任天堂角色、原版音乐与所有图像均获得了重新分发授权。该任务介绍还提到 `.nsf` 音乐资源，需要与引擎许可证分开记录、核对。引擎 GPL、任务贡献许可、第三方素材来源分别形成清单。

### 3.4 体积与复用边界

老游戏内容小，并不能直接推导网页版本下载量小。需要分别测量：马里奥的 JS 与音频、塞尔达的 WASM/运行库/任务/音乐，以及构建压缩后的首次传输量。仓库容量、Git LFS 指针大小和原版 ROM 大小都不能当成实际部署体积。

最终只发布所需运行文件和所选关卡内容。禁止把 ZQuest 的整个任务目录、编辑器、测试回放和所有音乐库默认预下载到博客首页。代码复用与素材发布条件分开验收，并提供第三方致谢与对应源码信息；iframe 的技术隔离不替代许可证要求。

## 4. 用户实际操作流程

### 4.1 从主页启动

1. 访客进入现有桌面 3D 场景，聚焦 Switch 屏幕后看到首页图标。
2. 图标顺序固定为：**塞尔达 → 马里奥 → 原有项目**。游戏不会随项目排序、分页或后台项目编辑而移动。
3. 点击或按 Enter 触发同一个打开逻辑，路由进入 `/games/zelda` 或 `/games/mario`。
4. Switch 屏幕显示该游戏的加载状态，只加载所选游戏。
5. 资源与本地存档准备好后进入游戏；存在兼容的自动存档时默认继续，没有存档时进入新游戏。游戏自己的标题画面可以保留。
6. 若音频因浏览器策略未启用，在游戏画面给出一次“按 Enter 开始/启用声音”的提示，不额外增加游戏选择页。

在未聚焦的 3D 屏幕上点到游戏图标时，应先完成现有聚焦动作，并保留这次待启动的游戏，聚焦后继续打开。一次操作只能创建一个实例。

### 4.2 暂停、继续与返回

暂停层由博客统一提供，至少包含：继续游戏、按键说明、声音、保存并返回主页。新游戏、备份导出/导入放在次级操作中。

- `Esc` 打开暂停层，不直接退出整个 Switch 屏幕。
- 暂停时冻结游戏逻辑、清空按住的方向键并停止游戏音频；继续后恢复焦点。
- 切换标签页、窗口失焦时暂停，返回后由用户继续，避免角色在不可见时死亡。
- “保存并返回主页”完成持久化后才销毁游戏，回到首页原来的游戏图标位置。
- 存档失败时保留当前会话，提供重试、导出备份，或由用户明确选择不保存离开。
- 浏览器后退、站内导航及场景的 Home 操作统一经过退出协调逻辑，避免绕过保存直接卸载。
- 浏览器原生全屏与 Switch 屏幕聚焦是不同状态；原生 Esc 退出全屏时也应正确暂停，不让第二层快捷键继续触发场景退出。

### 4.3 键盘方案

以下是建议映射，最终由适配器统一，界面提示必须与实测动作一致。

| 按键 | 首页 | 马里奥 | 塞尔达 |
| --- | --- | --- | --- |
| 方向键 | 移动选中项 | 左右移动，按游戏规则处理上下 | 四方向移动 |
| Enter | 打开选中图标 | 开始/游戏内确认 | Start/游戏内菜单 |
| Z | 不占用 | 跳跃 | A 动作，通常为剑 |
| X | 不占用 | 加速/火球 | B 道具 |
| Space | 不占用 | 不默认绑定 | 地图，遵循任务支持情况 |
| Esc | 沿用主页退出逻辑 | 博客暂停层 | 博客暂停层 |

游戏激活期间停用主页方向键、Enter、Esc 处理器。iframe 内按键需要由游戏适配器处理并发送暂停事件；不能依赖子页面的键盘事件冒泡到父页面。输入框、存档命名和文件选择器打开时，不转发游戏按键。

## 5. 与现有博客结构的结合

### 5.1 已定位的接入点

| 现有文件 | 现状 | 计划调整 |
| --- | --- | --- |
| `web/src/App.tsx` | `HomeEntry` 分流桌面场景与移动界面；旧 `/games` 是 Layout 下的占位页 | 新增游戏路由并继续走桌面 Switch 壳；移动端在加载运行时之前拦截；旧 `/games` 建议回到主页 |
| `web/src/features/switch-ui/switchRoutes.ts` | 暂无 game 路由种类 | 增加 `game` 与经过白名单验证的 `gameId` |
| `web/src/features/switch-ui/SwitchHomeScreen.tsx` | 首页项目卡与 Enter 行为面向项目详情，存在全局键盘处理 | 合成游戏和项目入口，使用统一打开函数，游戏期间暂停主页快捷键 |
| `web/src/features/switch-ui/ProjectCard.tsx` | 面向项目展示，含仓库相关动作 | 复用封面视觉；游戏使用独立卡片或明确类型分支，不显示仓库按钮 |
| `web/src/features/switch-ui/switchHomeData.ts` | 部分数据也被移动端引用 | 不直接在共享项目数据中插入游戏，使用独立桌面游戏注册表 |
| `web/src/scene/SwitchScreenOverlay.tsx` | 在 3D 屏幕内渲染 preview 形态首页 | 仅展示首页/静态预览，不在这里重复挂载游戏 |
| `web/src/scene/SceneEntry.tsx` | 管理镜头、场景和屏幕聚焦 | 协调唯一游戏容器、导航退出及背景渲染开销 |
| `web/src/features/switch-ui/MobileSwitchAppHome.tsx` | 独立移动首页 | 维持现有内容，不添加两个游戏入口 |
| `docker/nginx.conf` | SPA 回退与静态资源服务 | 实施阶段核对游戏资源 MIME、缓存与隔离响应头；本次不改动 |

游戏注册项独立于后端项目模型，建议使用 `game:mario`、`game:zelda` 等带类型的 UI 标识，路由使用稳定的 `mario`、`zelda`。不要复用项目 ID，也不要经过项目详情接口、后台项目 CRUD、项目排序或空卡片判断。

游戏固定置顶不占用现有“项目条目数量”的配置额度。“更多项目”和项目库只计算项目；首页的选中索引、左右边界与滚动位置则计算实际混合入口。

### 5.2 唯一运行实例与独立运行页

建议采用 **博客 React 外壳 + 同源独立游戏页 iframe + 每个游戏一个适配器**。

| 层 | 责任 |
| --- | --- |
| 主页与路由 | 固定图标、打开游戏、返回位置、桌面与移动端分流 |
| `GameSessionHost` | 维护唯一实例、状态机、暂停层、加载错误与生命周期 |
| iframe 内适配器 | 对接引擎启动/暂停/恢复/音频/保存，处理运行页输入 |
| 本地存档模块 | 格式与版本校验、持久化、备份、恢复和迁移 |
| 静态资源层 | 提供固定版本的游戏脚本、WASM、任务和音频 |

采用独立运行页的原因是 FullScreenMario 含全局状态，ZQuest 又有自己的 canvas、文件系统和 Worker。这样可以隔离样式、依赖与大部分生命周期，避免干扰博客 React 树。同源 iframe 不是阻止不可信代码访问站点数据的安全边界，所以第三方脚本仍需审阅，移除无关统计与外部加载。

现有屏幕存在 preview 与聚焦展示的区分，游戏容器必须放在唯一的活动展示层；不能把 iframe 放进每个 `SwitchHomeScreen` 实例。React 开发模式重复挂载、连续点击和快速切换游戏都要具备取消和清理机制。

建议的目录组织，均为待创建：

```text
web/src/features/games/
  gameRegistry.ts             # 桌面入口与运行资源元数据
  GameCard.tsx                # 游戏封面卡片
  GameSessionHost.tsx         # 唯一运行容器
  GamePauseMenu.tsx           # 暂停和本地备份操作
  gameProtocol.ts             # 父子页面消息类型
  gameSession.ts              # 会话、请求与退出协调
  saves/                     # 本地数据库、校验、迁移与导入导出

third_party/games/
  mario/                     # 固定版本源码、许可证、适配补丁
  zelda/                     # 固定版本引擎信息、任务来源、适配补丁
  sources.json               # 来源、版本、许可、文件校验值与构建说明

web/public/game-assets/
  mario/<build-id>/           # 构建产生的可部署运行文件
  zelda/<build-id>/           # 构建产生的可部署运行文件
```

引擎源码和构建产物分开管理。是否提交大型产物到 Git 由项目现有发布流程决定，但必须保留可重建的源码版本、补丁和构建步骤。路由 `/games/...` 与资源 `/game-assets/...` 分开，防止 SPA 回退把 HTML 当作 WASM/JS 返回。

### 5.3 运行协议与状态机

状态建议为：`idle → loading → booting → running ↔ paused → saving → leaving → idle`，任一步骤可进入可恢复的 `error` 状态。

| 方向 | 消息类别 | 含义 |
| --- | --- | --- |
| 子 → 父 | `READY` | 引擎及持久化存储已准备好，并报告支持哪些能力 |
| 父 → 子 | `START / PAUSE / RESUME` | 启动、暂停、继续 |
| 父 → 子 | `SAVE / LOAD / EXPORT / IMPORT` | 按游戏适配器执行存档操作 |
| 子 → 父 | `ACK / ERROR / PAUSE_REQUEST` | 返回操作结果、错误或请求显示博客暂停层 |
| 父 → 子 | `SET_VOLUME / DISPOSE` | 控制声音，完成退出前的清理 |

这些是本项目准备新增的协议，并非两个上游已经提供的 API。每条消息至少带 `protocolVersion`、`gameId`、`sessionId`，有结果的操作带 `requestId`。校验消息结构、`event.origin`、`event.source`，发送时指定准确目标源，不使用任意源广播。

`SAVE` 成功必须表示实际持久化成功，不能只代表已经把消息发给 iframe。超时或旧会话迟到的消息不能销毁新实例、覆盖新存档。保存与加载请求按会话串行处理，暂停后再读写一致状态。

上游无法支持的能力如“任意时刻快照”，应通过能力字段明确关闭；不提供表面可点、实际无效的按钮。

## 6. 只在浏览器保存的设计

### 6.1 数据边界

游戏静态文件可由博客服务器提供；**访客进度只存在访客浏览器中**。服务器不新增游戏存档接口或表，不使用账号同步，不进入现有 `api/saveQueue.ts`，也不把进度编码进 URL、日志、错误上报或统计事件。

| 数据 | 存放位置 | 处理原则 |
| --- | --- | --- |
| 马里奥进度 | 浏览器 IndexedDB | 本站适配器生成可恢复的结构化数据 |
| 塞尔达存档文件 | 引擎浏览器文件系统及其 IndexedDB 持久层 | 沿用引擎的存档格式和落盘流程 |
| 按键、音量、最近游戏 | 小型本地设置，可使用 localStorage | 不保存大块二进制状态 |
| 游戏资源缓存 | HTTP 缓存；以后如有需要再评估 Cache Storage | 和存档数据库分开清理 |
| 手动备份 | 访客通过下载获得的文件 | 导入导出完全在本地处理 |

“本地缓存”在实现上主要落到 IndexedDB，不能把用户进度放进会随静态资源更新整体清掉的资源缓存。不同浏览器、设备和源站各自保存；清除站点数据或使用临时浏览会影响保留。暂停菜单提供一句简短说明和导出入口。

### 6.2 存档语义

**马里奥首期采用关卡/检查点进度存档，不承诺模拟器式瞬时快照。** 至少保存当前世界与关卡、已完成进度、生命、分数、金币、角色状态，以及可以安全恢复的位置标识。只有在重载后可重建场景的安全边界才更新自动存档；菜单应显示最近保存的关卡或检查点。计时器、死亡中、传送中、动画中的状态如何归一化，要通过适配器验证。

**塞尔达采用引擎原生游戏存档。** Web 源码提供 `/local` 挂载与 IndexedDB 同步逻辑，可以复用，但必须在引擎写出存档后等待文件系统同步完成，再向博客报告成功。[Web 存储设置](https://github.com/ZQuestClassic/ZQuestClassic/blob/main/web/settings.js)、[运行与同步逻辑](https://github.com/ZQuestClassic/ZQuestClassic/blob/main/web/main.js)

ZQuest 的普通持久存档不必然等于暂停时的全部内存状态；必须实测保存位置、生命和道具恢复规则。原生保存可能受游戏阶段约束，“自动存档”只在已确认支持的安全时机调用。若无法无副作用地触发原生保存，就保留引擎的保存交互并明确显示保存状态，不能伪造成功。

需要避免两个具体错误：

- 不通过 Web Player 的 `test` 测试模式启动，官方界面明确说明这种模式不能保存；使用普通启动路径并在适配层选择固定任务。
- 不把引擎 IndexedDB 和博客另一份文件副本同时当作最新存档。引擎存档为唯一权威数据，博客只维护元信息；手动备份与槽位快照必须在引擎暂停、写入与同步完成后生成。

### 6.3 保存、恢复与备份

首期必须有可靠的自动/原生存档、继续游戏和手动导出/导入。额外的“1 个自动槽 + 3 个手动槽”作为增强项，等引擎完整存档单元和恢复规则验证后再启用，不强行套用同一种 JSON 格式。

统一的元信息建议包含：`schemaVersion`、`gameId`、`engineBuildId`、`contentVersion`、`savedAt`、存档类型、载荷校验值及可读进度摘要。马里奥载荷为版本化结构化数据，塞尔达载荷为恢复所必需的原生文件集合；不能未经确认就只复制某一个 `.sav` 文件。

保存流程：暂停/到达安全保存点 → 生成引擎存档 → 原子提交或完成引擎同步 → 更新元信息 → 返回保存成功 → 允许卸载。事务失败、存储配额不足、隐私模式限制均保留旧档，不用空档覆盖。

恢复流程：校验游戏和格式 → 校验任务/引擎兼容 → 在启动合适阶段恢复 → 成功后接收输入。不兼容的旧档先保留并允许导出；没有迁移程序时不自动覆盖。导入文件校验大小、结构和内容类型，不执行其中的脚本。

游戏运行期间在安全节点保存，页面隐藏时尽力保存。刷新、关标签或进程崩溃无法保证最后一次异步写入完成，因此不能仅依赖 `beforeunload`。已持久化的进度应在重开浏览器后恢复。[页面卸载事件的限制](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)

同源多标签同时启动相同游戏时，采用单写入会话锁或冲突提示，防止后打开的旧状态覆盖新档。存储键保持稳定，不随每次静态构建路径改变；升级游戏资源只更新资源缓存，不清空存档。

## 7. 性能、桌面边界与部署要求

### 7.1 加载与释放

- 首页只需要游戏元数据和封面，不能通过顶层 import、隐藏 iframe 或预取加载两套引擎。
- 点哪个游戏才加载哪个游戏；返回首页后静态 HTTP 缓存可保留，运行实例、Worker、事件监听和音频应释放。
- 游戏运行时控制后台 3D 场景持续渲染的开销；优先复用现有聚焦状态，在不破坏镜头和返回动画的条件下降低无意义帧更新。
- 保持游戏原始画面比例，像素画面使用清晰的缩放方式，允许留黑边，避免拉伸填满 16:9 屏幕。
- 显示真实加载状态；失败可重试或返回首页，不能让访客面对永久黑屏。
- 固定外部依赖并改为本站资源，不在运行时请求随机 CDN、公共任务清单或第三方统计脚本。

### 7.2 移动端与路由

使用现有 `HomeEntry` 的设备分流规则作为起点，不另加一套互相矛盾的宽度判断。移动端首页不展示游戏图标；直接访问 `/games/mario`、`/games/zelda` 时，仅显示“请在电脑端游玩”和返回入口，在此之前不导入游戏运行模块。

桌面游戏会话中窗口缩小触发移动布局时，先暂停并协调保存，再卸载；不能任由 `HomeEntry` 切换分支直接丢失进度。移动布局的测试同时覆盖触控设备与小窗口场景。

未知 `gameId` 显示可返回的错误状态，不请求任意资源地址。桌面刷新游戏深链接应恢复到 Switch 游戏壳，返回按钮回主页，而非掉进旧 Layout 游戏占位页。

### 7.3 ZQuest 的跨源隔离验证

当前多线程构建是塞尔达预选方案的重要前置条件。常规部署需要安全上下文、可用的 `SharedArrayBuffer`、正确的 COOP/COEP 与资源策略，并在实际运行上下文检查 `crossOriginIsolated`。[浏览器隔离条件](https://developer.mozilla.org/en-US/docs/Web/API/Window/crossOriginIsolated)

实施前要完成以下验证：

1. 在具有实际博客布局与资源来源的测试环境运行选定 Web 构建，核对顶层页面、同源 iframe 和 Worker 的隔离状态。
2. 检查远程图片、字体、GitHub 内容、模型和其他嵌入资源是否受 COEP 影响；先整理资源来源，再决定响应头范围。
3. 明确 SPA 导航不会重新获取顶层文档响应头。只给 `/games/zelda` 或 iframe 文件加头，不能假定从 `/` 单页跳转过来就能启用隔离。
4. 若需要调整整个桌面页面的响应头，必须回归博客原有功能。若当前站点无法兼容，再研究上游是否确实支持可维护的无多线程构建；不能假定删掉 `-pthread` 就可用。
5. 若上述条件不能满足，则塞尔达预选不通过。跳到独立新标签、改成不完整 JS 演示或改用模拟器均不属于本方案的默认替代。

静态资源部署还需确认：WASM 的 MIME 类型、Worker 与音频相对路径、压缩传输、版本缓存和文件缺失时真正返回 404。游戏 HTML 不使用永久缓存；带构建标识的资源可以长期缓存。域名、协议、端口或引擎数据库名变更时，应考虑本地存档迁移与导出提示。
